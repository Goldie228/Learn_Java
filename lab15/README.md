## 3. Слияние веток и merge-коммиты

Фактический граф истории после слияния всех пятнадцати веток:

```
<<<GIT_LOG>>>
```

Только коммиты слияния:

```
<<<GIT_MERGES>>>
```

Каждая ветка содержит один коммит с файлами работы, а слияние оформлено
отдельным merge-коммитом. История линейна по основной ветке, но сохраняет
границы всех пятнадцати веток.

## 4. Разрешение конфликта слияния

Конфликт воспроизведён в отдельном временном репозитории, чтобы не засорять
историю основного проекта. Обе ветки изменили одну и ту же строку
`app.version` в файле `app.properties`.

Создание ситуации:

```bash
git init -b main
printf 'app.name=demo\napp.version=1.0\napp.author=student\n' > app.properties
git add app.properties
git commit -m "initial: базовые настройки"

git checkout -b feature/version
sed -i 's/app.version=1.0/app.version=2.0/' app.properties
git commit -am "feature: версия 2.0"

git checkout main
sed -i 's/app.version=1.0/app.version=1.1/' app.properties
git commit -am "main: версия 1.1"
git merge feature/version
```

Фактический вывод слияния:

```
Автослияние app.properties
КОНФЛИКТ (содержимое): Конфликт слияния в app.properties
Сбой автоматического слияния; исправьте конфликты, затем зафиксируйте результат.
```

Файл после конфликта:

```properties
app.name=demo
<<<<<<< HEAD
app.version=1.1
=======
app.version=2.0
>>>>>>> feature/version
app.author=student
```

`HEAD` — текущая ветка `main` (версия 1.1), ниже — вариант из
`feature/version` (версия 2.0). Конфликт разрешён вручную: выбрана версия 2.0,
зафиксированная как 1.2.

```bash
printf 'app.name=demo\n# итог разрешения конфликта: берём версию 2.0 и фиксируем её как 1.2\napp.version=1.2\napp.author=student\n' > app.properties
git add app.properties
git commit -m "merge: разрешён конфликт версий (1.1 + 2.0 -> 1.2)"
```

Результат:

```
*   c03bc7d (HEAD -> main) merge: разрешён конфликт версий (1.1 + 2.0 -> 1.2)
|\
| * 9cadda3 (feature/version) feature: версия 2.0
* | f794e4d main: версия 1.1
|/
* 3f4d1be initial: базовые настройки
```

Маркеры `<<<<<<<`, `=======`, `>>>>>>>` удалены, конфликтующий файл добавлен
в индекс, слияние завершено отдельным коммитом. При необходимости отменить
слияние можно командой `git merge --abort`.

## 5. Удалённый репозиторий и Pull Request

Git — распределённая система: каждый клон содержит всю историю. GitHub —
платформа для хранения удалённых репозиториев и код-ревью.

Последовательность для публикации:

```bash
git remote add origin https://github.com/<user>/Learn_Java.git
git remote -v
git push -u origin main
git push origin --all
git ls-remote --heads origin
```

Проверка отправки выполнялась на локальном bare-репозитории (эквивалент
удалённого, но без сетевой аутентификации):

```
<<<REMOTE_LS>>>
```

После проверки remote удалён, чтобы репозиторий не зависел от временного пути:

```bash
git remote remove origin
```

Порядок работы через Pull Request на GitHub:

1. создать ветку `lrN` и закоммитить changes;
2. `git push -u origin lrN`;
3. на GitHub нажать «Compare & pull request»;
4. заполнить описание (что добавлено и зачем), пройти код-ревью;
5. нажать «Merge pull request» — GitHub создаст merge-коммит;
6. удалить ветку на GitHub и локально: `git branch -d lrN`.

Для реального GitHub требуется аутентификация (Personal Access Token или
SSH-ключ) и двухфакторная аутентификация для авторов кода. Локальный
bare-репозиторий позволяет проверить те же команды `remote`, `push` и
`ls-remote` без публикации учебного проекта.

## 7. Ответы на контрольные вопросы

1. **Что такое система контроля версий и зачем она нужна?** Это хранилище
   истории изменений файлов. Она позволяет вернуться к любой версии, откатить
   ошибочные изменения, работать параллельно и видеть авторство.
2. **Чем Git отличается от SVN и Perforce?** Git распределённый: каждый клон
   содержит всю историю, большинство операций локальны, данные хранятся как
   снимки с контрольными суммами SHA-1, а не как набор дельт.
3. **Три состояния файла:** modified (рабочая директория), staged (индекс),
   committed (репозиторий).
4. **Основные команды:** `init`, `clone`, `status`, `add`, `commit`, `log`,
   `diff`, `branch`, `checkout/switch`, `merge`, `pull`, `push`.
5. **Что такое ветка?** Независимая линия разработки — подвижная ссылка на
   коммит. Позволяет вести работу, не затрагивая стабильный `main`.
6. **Конфликт слияния** возникает, когда две ветки изменили один участок
   файла. Его разрешают вручную: убирают маркеры, оставляют нужный текст,
   выполняют `git add` и `git commit`.
7. **Git и GitHub:** Git — локальная VCS, GitHub — платформа для удалённых
   репозиториев, PR и совместной работы.
8. **Pull Request** — предложение влить ветку в основную ветку репозитория;
   позволяет обсудить изменения и провести код-ревью до слияния.
9. **`.gitignore`** перечисляет файлы и каталоги, которые Git не отслеживает:
   артефакты сборки, настройки IDE, логи, секреты.
