# Конспект: Git и GitHub

## 1. Система контроля версий

**Система контроля версий (VCS)** — это система, которая записывает изменения
файлов во времени и позволяет вернуться к любой сохранённой версии. VCS хранит
историю, показывает, кто и когда вносил изменения, позволяет откатить ошибочный
коммит и работать параллельно нескольким разработчикам.

Поколения VCS:

| Поколение | Примеры | Особенность |
|-----------|---------|-------------|
| Локальные | RCS | История хранится на одном компьютере |
| Централизованные | CVS, SVN, Perforce | Единый сервер — единая точка отказа |
| Распределённые | Git, Mercurial | Каждый клон содержит всю историю |

## 2. Ключевые особенности Git

- **Снимки, а не различия.** Каждый коммит — снимок всего проекта; неизменённые
  файлы переиспользуются по ссылке.
- **Локальность.** Почти все операции выполняются без сети.
- **Целостность.** Содержимое объектов проверяется контрольными суммами SHA-1.
- **Только добавление.** Откат оформляется новым коммитом, история не теряется.

## 3. Три состояния файла

| Состояние | Где находится | Описание |
|-----------|---------------|----------|
| Modified | рабочая директория | файл изменён, но не подготовлен |
| Staged | индекс (staging area) | изменения войдут в следующий коммит |
| Committed | репозиторий | изменения сохранены в истории |

Схема: рабочая директория → `git add` → индекс → `git commit` → репозиторий.

## 4. Создание репозитория

```bash
git init                  # новый локальный репозиторий
git clone <url>           # копия удалённого репозитория
git status                # состояние файлов
```

Минимальная настройка автора:

```bash
git config --global user.name "Имя"
git config --global user.email "mail@example.com"
```

## 5. Основные команды

```bash
git add <файл>            # подготовить файл
git add .                 # подготовить все изменения
git commit -m "сообщение" # зафиксировать индекс
git log --oneline         # краткая история
git log --graph --oneline --decorate --all
git diff                  # изменения вне индекса
git diff --staged         # изменения в индексе
git show <commit>         # содержимое коммита
```

Хорошее сообщение коммита отвечает на вопрос «что и зачем сделано»:
`feat(lab8): добавить иерархию Computer/GamingPC/OfficePC`.

## 6. Ветки

**Ветка** — независимая линия разработки, то есть подвижная ссылка на коммит.
Основная ветка обычно называется `main` (ранее `master`).

```bash
git branch                # список веток
git branch lr8            # создать ветку
git checkout lr8          # переключиться
git switch -c lr8         # создать и переключиться (современный синтаксис)
git merge lr8             # слить ветку в текущую
git branch -d lr8         # удалить слитую ветку
```

## 7. Слияние и конфликты

**Fast-forward** — если целевая ветка не ушла вперёд, Git просто переносит
указатель, отдельного коммита слияния нет. **Слияние с merge-коммитом**
(`git merge --no-ff`) всегда создаёт отдельный коммит с двумя родителями; это
удобно, чтобы в истории была видна граница ветки.

Конфликт возникает, когда обе ветки изменили одну и ту же часть файла.
Git помечает участок маркерами:

```
<<<<<<< HEAD
значение из текущей ветки
=======
значение из сливаемой ветки
>>>>>>> feature
```

Порядок разрешения:

1. открыть конфликтующий файл и выбрать/объединить нужный вариант;
2. удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`;
3. `git add <файл>`;
4. `git commit` (Git подставит стандартное сообщение о слиянии).

Отказаться от слияния можно командой `git merge --abort`.

## 8. Удалённые репозитории и GitHub

```bash
git remote add origin https://github.com/user/repo.git
git remote -v
git push -u origin main
git fetch origin
git pull
```

**Git** — локальная распределённая VCS. **GitHub** — платформа для хранения
удалённых репозиториев, код-ревью и совместной работы.

**Pull Request (PR)** — предложение влить изменения из ветки в основную ветку
репозитория. Порядок: создать ветку → закоммитить → `git push` → на GitHub
«Compare & pull request» → описание и ревью → «Merge pull request».

Для отправки изменений GitHub требует аутентификацию (Personal Access Token
или SSH-ключ) и двухфакторную аутентификацию для авторов кода.

## 9. .gitignore

Файл `.gitignore` перечисляет шаблоны того, что Git не должен отслеживать.
Для Java-проекта:

```gitignore
target/
*.class
*.jar
.idea/
*.iml
.vscode/
*.log
```

Скомпилированные файлы и настройки IDE не должны попадать в репозиторий;
файлы с паролями и ключами — тем более.

## 10. Проверка результата

```bash
git status                  # рабочая директория чиста
git branch -a               # все ветки
git log --graph --oneline --decorate --all
git log --merges --oneline  # только коммиты слияния
```

Если рабочая директория чиста, все ветки слиты, а `git log --merges` показывает
нужные слияния, работа выполнена корректно.
