«Основы кроссплатформенного программирования». Все работы — отдельные Maven-проекты
в каталогах `lab8` … `lab15`, стилистически совместимые с `lab4`–`lab7`.

## 3. Этапы

### Этап 0. Подготовка
1. Прочитать методичку работы, определить задание варианта 9.
2. Зафиксировать перечень классов, полей, методов и ожидаемых сообщений.
3. Проверить окружение: JDK 21+, Maven 3.9+, Git.

### Этап 1. Реализация (исполнитель)
Для каждой работы создать:

```
labN/
├── pom.xml
├── task.md            — исходное задание варианта
├── conspectus.md      — краткий конспект теории
├── README.md          — отчёт: задание, реализация, запуск, тесты, вывод программы
└── src/
    ├── main/java/by/epam/learn/…   — классы работы + Main с меню
    └── test/java/by/epam/learn/LabNTest.java
```

Требования:
- `groupId=by.epam.learn`, `artifactId=labN`, `maven.compiler.release=21`,
  UTF-8, JUnit 4.13.2 (`scope=test`);
- пакет `by.epam.learn`, `Main` с интерактивным меню;
- вся бизнес-логика вынесена в отдельные классы и покрыта JUnit-тестами;
- в коде — только технические комментарии; персональные данные (группа, страна,
  дата) в комментарии не попадают;
- сообщения и вывод — на русском языке, как в методичках.

### Этап 2. Самопроверка (исполнитель)
```bash
cd labN
mvn -q clean test
mvn -q package
printf '…\n' | java -cp target/classes by.epam.learn.Main
```
Вывод программы дословно переносится в `README.md`. Не допускается выдуманный вывод.

### Этап 3. Независимая проверка (ревьюер)
1. Сверить состав классов/методов с методичкой (таблица в §1).
2. Проверить, что тесты действительно проверяют логику, а не только геттеры.
3. Проверить отрицательные сценарии (исключения, пустые коллекции, границы).
4. Запустить сборку и программу, сравнить вывод с README.
5. Сформировать список замечаний; оркестратор вносит исправления.

### Этап 4. Git-интеграция (интегратор)
1. `git init -b main`, `.gitignore` (`target/`, `*.class`, IDE, логи, `lab14/data/`).
2. Начальный коммит с методичками и `WORKFLOW.md`.
3. Для каждой работы: ветка `lrN` от актуального `main` → коммит → merge в `main`
   с `--no-ff` (отдельный merge-коммит).
4. Конфликт слияния демонстрируется в отдельном временном репозитории, транскрипт
   переносится в отчёт ЛР15.
5. `git log --graph --oneline --decorate` и `git branch -a` — в отчёт ЛР15.

### Этап 5. Финальный аудит
- [ ] `mvn clean test` зелёный во всех восьми проектах.
- [ ] `Main` запускается без исключений, меню обходит все пункты.
- [ ] Отчёт соответствует фактическому поведению программы.
- [ ] Все пункты варианта 9 закрыты.
- [ ] В репозитории нет `target/`, `*.class`, временных файлов.
- [ ] История Git содержит 15 merge-коммитов и ветки `lr1`…`lr15`.

## 4. Definition of Done

Работа считается готовой, если одновременно выполнено:

1. проект собирается командой `mvn clean package`;
2. `mvn test` — 0 failures, 0 errors, число тестов ≥ 3;
3. программа запускается и демонстрирует все пункты задания;
4. `README.md` содержит задание, структуру, команды, реальный вывод и раздел
   «Теория для защиты»;
5. замечания ревьюера закрыты.
